# 计划：修复 IMA 长回答截图「不完整 / 重复堆叠」

> 本文件按「先定计划再动手」原则产出（协作规则 方法14）。
> 当前状态：2026-07-13，死循环第 3 轮，必须换思路（规则5 / 方法18）。

## 1. 问题定义
监控脚本需把 IMA 窗口里「回答区」的长答案完整截成一张纵向长图发到微信群。
- 现象 1（早期）：只截到单屏 ~758px，回答被截断。
- 现象 2（本轮重写后）：拼接出 91213px 的巨型图（正常仅 ~5276px），内容大量重复。
- 验收标准：
  1. 发出的图纵向连续、无跳段丢失、无重复堆叠；
  2. 图高与真实答案篇幅成正比（中等答案几千 px，不出现 9 万 px）；
  3. 左导航栏不在裁剪范围内（此前已修复，需保持）。

## 2. 根因分析（基于 diag2 实测）
- `pyautogui.scroll(-8)` 在 IMA webview 里滚动量不稳定（实测相邻帧位移在 12~736px 间跳变）。
- 旧拼接逻辑依赖 `_find_overlap(result, img)` 的像素重叠匹配；当重叠匹配返回 0 时，
  代码错误地 `append` 了**整屏 758px**，且「到底」判定 `k >= 0.92*img.height` 永远不成立 → 循环跑满 120 次、每步整屏堆叠 → 91213px 重复图。
- 根因一句话：**拼接依赖不可靠的像素重叠匹配，且无有效的「无进展即停」兜底。**

## 3. 候选修复方案（方法18：先列方案再动手）
- **方案 A（采用）：逐帧精确位移拼接**
  不用「 growing result 底部 vs 新帧顶部」的重叠匹配，改为对**相邻两帧原始截图**做整图相关，算出本步真实位移 `d`（IMA 回答区为纯文本块，灰度相关稳定），只追加新帧底部 `d` 行。
  无论滚动量是否稳定，`d` 实测即得，理论上不会整屏堆叠或跳段。
  优点：对滚动量不一致免疫；到底时 `d→0` 自然停。
- **方案 B：固定步长 + 确定式裁剪**
  先标定 `scroll(N)` 的精确像素位移，之后每步按固定裁剪量拼接。
  缺点：滚动量实测本就跳变（12~736），固定值会错位，已证明不稳。
- **方案 C：改用键盘 PageDown / End 滚动**
  换滚动输入源，可能更稳。
  缺点：仍依赖重叠匹配去重，未解决根本的匹配脆弱问题；且与 A 不冲突，可作为 A 的输入源优化。
- **方案 D：切换到网页版 LLM 求解（规则 方法11）**
  把代码与问题贴给网页版 LLM 求更优解。
  决定：先执行方案 A（本地可收敛）；若仍失败，再用方法11 切战场。

## 4. 实施步骤（小步，规则7）

2. 重写 `_capture_full_answer`：滚到顶 → 逐帧 `grab` → 算 `d` → 只追加底部 `d` 行 → `d<=阈值` 连续 2 次即停。
3. 写 `diag3.py` 打印每步 `d` 与最终 `H`，验证无重复（H 应为几千 px 级）。
4. 验证通过后跑一次 live，确认真发图且完整。
